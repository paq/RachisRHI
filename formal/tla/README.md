## Model scope & backend coverage

- **Retention criterion:** A formal model is kept only when exhaustive action ordering contributes a guarantee that ordinary executable tests do not provide—multi-owner lifetime, transactional publication and rollback, concurrency and lock ordering, queue/fence timelines, or arbitrary lifecycle interleavings.
- **Test-owned linear contracts:** Short linear capability, validation, and data-mapping contracts belong to Catch2 tests under `tests/`. One intentional exception is `AttachmentContentValidity.tla`, which remains formal because undefined attachment content is a temporal caller-contract state that deterministic rendering tests cannot safely observe or assert after a discard.
- **Native & C ABI correspondence:** *Native correspondence* below refers to the C++23 implementation under `src/` and `include/Rachis/`. RachisRHI also exposes a versioned C11 ABI through `include/Rachis/rachis.h` and `src/C/` ([`docs/c-abi.md`](../../docs/c-abi.md)).

| Coverage slice | Module count | Scope note |
| --- | --- | --- |
| Total formal modules | 97 | Exhaustive finite-state models checked by TLC |
| Direct3D 12 / portable only | 67 | Name only Direct3D 12 or portable code in native correspondence |
| Vulkan correspondence | 26 | Also name `src/Vulkan/` modules |
| Metal correspondence | 16 | Name `src/Metal/` modules |

> [!NOTE]
> A contract checked for one backend in TLA+ is not automatically model-checked for the others, even where the backends share the same public RHI rule.

## Running TLC

```bash
bash tools/tlc.sh                                       # every configuration in formal/tla
bash tools/tlc.sh --small                               # configurations not marked `\* Size: large`
bash tools/tlc.sh formal/tla/CommandDependencyPublication.cfg \
                  formal/tla/MetalCommandRetention-callbacksink.cfg
```

Run TLC through `tools/tlc.sh`: it bounds every run with `TLC_TIMEOUT` (`1800` seconds by default), closes stdin, writes TLC working state to a temporary directory, and verifies that every configuration reaches the exact verdict declared in its header:

| Configuration pattern | Expected verdict | Purpose |
| --- | --- | --- |
| `<Module>.cfg` | `\* Expect: pass` | Checks `<Module>.tla` with all design rules enabled |
| `<Module>-<label>.cfg` | `\* Expect: invariant <Name>`, `property <Name>`, or `deadlock` | Disables one design rule (`CONSTANT`; `QueueLockOrdering-deadlock.cfg` disables two) so an ineffective invariant fails `tools/tlc.sh` |
| `BindingPoolLifecycle-singleversion.cfg` | `\* Expect: pass` | Positive variant that keeps every rule enabled while shrinking the pool to one version slot |

Environment variables:
- `TLA2TOOLS` (required): path to `tla2tools.jar` (`1.8.0+`).
- `JAVA` or `JAVA_HOME`: selects the Java `11+` runtime.
- `TLC_TIMEOUT`: per-configuration timeout in seconds (default `1800`).
- `TLC_WORKERS`: overrides worker thread count (default `auto`). Configurations that expect a violation always run with one worker, so that TLC reports the same violated invariant on every run.

## Trusted boundary

TLC proves the stated invariants and action properties over each module's finite abstraction. It does **not** prove:

- **Driver and GPU behavior:** Direct3D 12, DXGI, WARP, Vulkan ICDs, and Apple Metal 4 runtime/driver behavior.
- **Model-to-code equivalence and C++ memory safety:** Models are written by hand from the native implementation and contract docs, not mechanically extracted from C++23 or Objective-C++. Catch2 contract tests (unit, WARP, Vulkan, Metal, and `RachisCAbi*`) and native validation layers cover those implementation boundaries.
- **Bounds:** Bugs that require larger object, queue, or timeline cardinalities than a configuration's finite bounds sit outside TLC's state graph.
- **Tooling and `StepSafety` vacuity:** Java and `tla2tools.jar` are checked against both positive and counterexample configurations so a broken runner fails closed, while a vacuous invariant fails closed only when a counterexample configuration expects its violation. Of the 55 counterexample configurations across 36 modules, 53 expect an invariant violation, `QueueLockOrdering-deadlock.cfg` expects a deadlock, and `PipelineStatisticsQuery-endstatistics.cfg` is the one configuration expecting a property violation (`StatisticsEndOnBeginSide`). No configuration expects a `StepSafety` violation, so the `StepSafety` action properties of the 90 modules that state one are still not checked for vacuity.
